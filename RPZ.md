# 1. Цель

Разработать систему, включающую веб-сервис и веб-приложение, в которой создатели публикуют квантовые вентили с изображением, коротким видео, углами X и Y, а пользователи просматривают и сравнивают вентили для оценки параметров квантовых вычислений.

# 2. Назначение

Система предназначена для просмотра и публикации квантовых вентилей (CNot, Hadamard, Pauli X/Y/Z, Phase S). В системе работают две группы пользователей. Гость просматривает вентили в виде плитки и ленты и фильтрует их по углам X и Y. Создатель после аутентификации дополнительно добавляет вентили с изображением и видео, публикует их, удаляет свои вентили и ставит лайки. Для сравнения используются углы X и Y в градусах.

3.4. Добавление аутентификации и авторизации, Swagger в веб-сервис и подготовка ТЗ (Python, FastAPI, Redis, сессии, Swagger, Microsoft Word).

3.6. Добавление авторизации и создания вентилей через Redux Toolkit и redux-thunk, кодогенерация взаимодействия с API через Axios; реализация удаления и лайков (React, Redux Toolkit, redux-thunk, Axios, Swagger).

3.7. Внедрение менеджера состояний для хранения фильтра углов, адаптивности и PWA, создание нативного приложения для гостя и развёртывание на веб-сервере (Redux Toolkit, CSS, PWA, Tauri, HTTPS).

3.8. Подготовка интерактивной демо-версии четырёх страниц приложения с переходами и стадиями добавления вентиля (Figma).

3.9. Подготовка документации: РПЗ, ТЗ, таблица методов веб-сервиса, UML и ER-диаграммы (Microsoft Word, draw.io).

# 4. Функциональные требования

## 4.1. HTTP методы

4.1.1. GET /api/gates - Список опубликованных вентилей с фильтром по углам X и Y и признаком принадлежности создателю

4.1.2. GET /api/gates/feed - Лента: первый опубликованный вентиль, вентиль по id или следующий после указанного

4.1.3. GET /api/gates/draft - Черновик вентиля текущего пользователя, id не указывается

4.1.4. POST /api/gates - Добавление черновика вентиля с изображением и видео

4.1.5. PUT /api/gates/{id}/publish - Публикация своего черновика вентиля

4.1.6. DELETE /api/gates/{id} - Логическое удаление своего вентиля

4.1.7. POST /api/gates/{id}/likes - Постановка или отмена лайка вентиля

4.1.8. POST /api/users/register - Регистрация

4.1.9. POST /api/users/login - Аутентификация

4.1.10. POST /api/users/logout - Деавторизация

## 4.2. Меню

4.2.1. Доступно гостю и создателю, отображается внизу всех страниц приложения

4.2.2. Лента - переход на страницу 4.5.

4.2.3. Добавление (доступно создателю) - переход на страницу 4.6.

4.2.4. Плитка - переход на страницу 4.4.

4.2.5. Вход (доступно гостю) - переход на страницу 4.3.

4.2.6. Выход (доступно создателю) - вызов метода 4.1.10.

## 4.3. Аутентификация

4.3.1. Доступна гостю

4.3.2. Отображает форму аутентификации и регистрации: поле логина, поле пароля

4.3.3. Войти - вызов метода 4.1.9., после успешного входа переход на страницу 4.4. в интерфейсе создателя

4.3.4. Зарегистрироваться - вызов метода 4.1.8.

## 4.4. Плитка вентилей

4.4.1. Доступна гостю и создателю

4.4.2. Отображает карточки опубликованных вентилей (вызов метода 4.1.1.): изображение, название, углы X и Y, количество лайков

4.4.3. Фильтр по углам X и Y: два двойных слайдера и кнопка "Применить" - вызов метода 4.1.1. с параметрами angle_x_min, angle_x_max, angle_y_min, angle_y_max

4.4.4. Нажатие на карточку - переход на страницу 4.5. с выбранным вентилем, вызов метода 4.1.2. с параметром id

4.4.5. Удалить (доступно создателю для своих вентилей при is_creator=1) - вызов метода 4.1.6.

4.5.1. Доступна гостю и создателю

4.5.2. Отображает один вентиль на весь экран (вызов метода 4.1.2.): вертикальное видео, название, описание с «Ещё…», углы X и Y, количество лайков

4.5.3. Следующий вентиль - вызов метода 4.1.2. с параметрами id и next=true

4.6.1. Доступна создателю

4.6.2. При открытии загружает черновик текущего пользователя (вызов метода 4.1.3.)

4.6.3. Отображает форму вентиля: фото над видео, название; выбрать файлы можно только до нажатия «Далее»

4.6.4. Далее - создание черновика вызовом метода 4.1.4. с названием, изображением и видео

4.6.5. Опубликовать - вызов метода 4.1.5. с названием, описанием, углами X и Y

# 5. Требования к аппаратному обеспечению

## 5.1. Расчет требуемых аппаратных характеристик сервера

Для проектного расчёта принимаются: 250 создателей, один новый вентиль от каждого создателя в сутки, 1000 гостей, по 20 запросов просмотра от гостя в сутки и рабочий день 8 часов. Это расчётный сценарий эксплуатации. Восемь запросов на публикацию и просмотр вентиля соответствуют рисунку 3: вход, список, создание, черновик, публикация, лента, следующая карточка и лайк. Запросы получения медиа в расчёт API не входят.

N_вентилей_сутки = 250 × 1 = 250 вентилей/сутки

N_HTTP_сутки = 250 × 8 + 1000 × 20 = 22 000 запросов/сутки

RPS_вентилей = 22 000 / (8 × 3600) ≈ 0,764 запроса/с

По методике принимается условная производительность одного ядра 500 запросов/с и коэффициент запаса 1,5. Число ядер округляется вверх, на каждое ядро предусматривается 4 ГБ оперативной памяти. Производительность уточняется нагрузочным тестированием при развёртывании.

N_ядер = (0,764 / 500) × 1,5 = 1 ядро

RAM_сервера = 4 × 1 = 4 ГБ

Расчётный минимум для API — 1 ядро и 4 ГБ ОП. Для совместной работы Python, PostgreSQL, Redis, MinIO и контейнеров на одном сервере предусматриваются 2 ядра и 8 ГБ ОП. Это сохраняет соотношение 4 ГБ на ядро и даёт ресурс для хранилищ и обработки загружаемых файлов.

Для оценки размера базы данных за пять лет берётся структура текущих таблиц. Размеры строковых полей оцениваются по верхней границе UTF-8: до 4 байт на символ. BIGINT и целые поля Python int на сервере amd64 принимаются по 8 байт, TIMESTAMP — 8 байт, BOOLEAN — 1 байт. Видеофайлы и изображения хранятся отдельно от БД.

Таблица 1 – Оценка объема, занимаемого одним вентилем

| Таблица | Поля и расчёт полезных данных | Размер |
|---------|------------------------------|--------|
| gates | id, creator_id, angle_x, angle_y: 4 × 8; title, summary, status, image_url, video_url: (128 + 512 + 16 + 255 + 255) × 4 | 4672 байт |
| likes | id, user_id, gate_id: 3 × 8 | 24 байта |
| users | id: 8; username: 64 × 4; email: 128 × 4; password: 128 × 4 | 1032 байта |

Принимаются в среднем три записи лайков на вентиль.

S_вентиля_с_лайками = 4672 + 3 × 24 = 4744 байт

N_вентилей_год = 250 × 365 = 91 250 вентилей/год

V_БД_год = 91 250 × 4744 / 1 073 741 824 ≈ 0,402 ГиБ/год

Начальные записи 250 создателей и 1000 зарегистрированных пользователей в этом сценарии требуют не более 1250 × 1032 = 1 290 000 байт; гости без регистрации записей users не создают. Для размеров строк PostgreSQL, индексов и служебных данных принимается коэффициент 2.

V_БД_5лет = 2 × (5 × V_БД_год + 1 290 000 / 1 073 741 824) ≈ 4,024 ГиБ

## 5.3 Расчёт диска с учётом фото и видео

Средний объём фото принимается 1 МиБ, короткого видео — 5 МиБ. Медиа новых вентилей сохраняются в течение пяти лет, в том числе для логически удалённых записей. Для ОС, образов контейнеров и статических файлов принимается дополнительный запас 30 ГиБ.

V_медиа_5лет = 250 × 365 × 5 × (1 + 5) / 1024 ≈ 2673,34 Ги

V_диска = 4,024 + 2673,34 + 30 ≈ 2707,36 ГиБ ≈ 2,91 ТБ

Для указанного сценария требуется диск не менее 4 ТБ. Резервная копия хранится на отдельном носителе. Значение 6 МиБ на вентиль является средним, а не пределом загрузки: при фактических размерах до 10 МиБ для фото и 50 МиБ для видео потребность MinIO пересчитывается по формуле 10. Для учебного стенда с небольшим набором вентилей допускается начальный диск 40 ГБ с возможностью расширения.

## 5.2 Сервер

5.2.1 Процессор x86-64 или ARM64 — не менее 2 ядер для совместного размещения компонентов.

5.2.2 Оперативная память — не менее 8 ГБ.

5.2.3 Дисковое пространство — не менее 4 ТБ для пятилетнего расчётного сценария.

5.2.4 Сетевой интерфейс — 1 Гбит/с; сервер должен быть доступен клиентам по сетевому адресу.

## 5.3 Клиент

5.3.1. Компьютер или мобильное устройство с процессором не менее 2 ядер и ОП не менее 4 ГБ для ОС и браузера.

5.3.2. Свободное пространство — не менее 1 ГБ для браузерного кеша и PWA; экран шириной от 360 пикселей.

5.3.3. Соединение с сервером — не менее 10 Мбит/с для воспроизведения короткого видео; поддержка аппаратного либо программного декодирования MP4.
